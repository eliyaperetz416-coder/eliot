# Accounts (Google sign-in, sync, onboarding, rest alarm) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development (recommended) or executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- Every user signs in once with Google.
- Their data is saved in Supabase and synced (the last change wins).
- Backups are gone.
- Onboarding asks one question per screen, including install, notifications and consent.
- The end of a rest alerts the user even with the phone locked.

**Architecture:**
- **Auth.** Hand-written PKCE client for Supabase Auth over `fetch`, with no SDK, like `crew-api.js`. The session lives in IndexedDB.
- **Sync.** One row per user, `public.user_data`, holds the existing backup snapshot (`collectData()` plus the crew token). A pure decision module chooses push, pull or merge, and a thin UI module runs it on change (debounced), on open and when the phone is back online.
- **Rest alarm.** A row in `public.rest_alarms`. A `pg_cron` job every 5 s hands due rows to a new edge function, `rest-push`, which sends Web Push. The existing `notify` function is not touched.
- **Additive only.** Every server change only adds tables and functions, so the live app (v1.47.1 on main) keeps working.

**Tech Stack:** Plain ES modules, IndexedDB, Supabase (Auth, PostgREST, `pg_cron`, `pg_net`, Edge Functions on Deno with `web-push`), `node --test`, Playwright smoke test with mocked Supabase routes.

**Spec:** `docs/superpowers/specs/2026-11-22-redesign-accounts-design.md`, section 4 and the 22.11 updates in sections 2 and 4.

## Global Constraints

- **Branch only.** Develop and push on `claude/mah-kora-ascpov`. **No PR to main and no production release** until launch day (spec section 2). Test on the Vercel preview URL of this branch.
- **Server changes are additive.** Do not alter or drop anything v1.47.1 uses: crew tables and functions, `notify`, and the `push_subs` trigger. Every migration is dry-run first, inside a transaction that ends in a raised exception. Read the results, confirm nothing persisted, then apply.
- **Sign-in is Google only.** No email login in this release.
- **Consent.** The checkbox is unchecked by default, and the sign-in button stays disabled until it is ticked. Store `consent_at` and `consent_version` (= `PRIVACY_VERSION`).
- **iPhone in Safari (not installed):** the install screen comes before sign-in, with "continue in browser".
- **Repo rules.** No Hebrew literals in `src/ui`, he/en key parity, `npm run stamp` before every commit, and all user-visible text through i18n.
- **Secrets.** The Google client secret is entered by Elia in the Supabase dashboard only, never in chat or in the repo. The VAPID private key stays in `app_config`.
- **Limits.** Sync payload ≤ `MAX_SYNC_BYTES = 8_000_000`. Push debounce `SYNC_DEBOUNCE_MS = 3000`. Token refresh when it expires within `REFRESH_SKEW_S = 60`.

## Review Focus

1. **First sign-in on a bad network with lots of local data.** If the upload fails, nothing local is lost, the app keeps working, and it retries later. "Migrated" is marked only after the server confirms. → sync tests in Task 4.
2. **Returning from Google with no saved PKCE verifier** (another browser context, or cleared storage). The user should see "sign-in didn't finish, try again", not a blank page or a loop. → auth test in Task 3.
3. **Days offline, then the token is revoked or the refresh fails.** The app keeps working on local data and shows sign-in again without wiping anything. → tests in Tasks 3 and 4.
4. **An old phone opens after a newer phone pushed.** The old phone pulls. It must not overwrite the newer data with its stale copy. → `decideSync` cases in Task 4.
5. **Too much data** (many custom-exercise photos) exceeds `MAX_SYNC_BYTES`. The user gets a clear message, local data stays, and the other syncs are not blocked forever. → sync test in Task 4.

**Files:**

**Interfaces (produced):**
- `src/core/pkce.mjs`:
  - `verifierFrom(bytes: Uint8Array) -> string` (base64url, 43+ characters)
  - `challengeS256(verifier: string) -> Promise<string>` (`crypto.subtle` SHA-256, base64url, no padding)
  - `sessionFrom(json, nowMs) -> { accessToken, refreshToken, expiresAt, user: { id, email, name } }` (`expiresAt` = nowMs + expires_in × 1000; `name` from `user_metadata.full_name`)
  - `needsRefresh(session, nowMs) -> boolean` (true when `expiresAt - nowMs < REFRESH_SKEW_S × 1000`)
- `src/ui/auth.js`:
  - `startGoogleSignIn() -> void`: saves the verifier in kv `pkce`, then sets `location.href` to `${url}/auth/v1/authorize?provider=google&redirect_to=${origin+pathname}&code_challenge=…&code_challenge_method=s256`.
  - `completeSignIn() -> Promise<'none'|'ok'|'error'>`:
    - On `?code=`, it POSTs `/auth/v1/token?grant_type=pkce` with `{ auth_code, code_verifier }`, saves kv `session`, deletes kv `pkce`, and strips the query with `history.replaceState`.
    - With a code but no verifier, it returns `'error'`. It also returns `'error'` on `?error=`.
  - `getSession() -> Promise<Session|null>`:
    - Refreshes when `needsRefresh` (`grant_type=refresh_token`).
    - When offline, it returns the stored session as it is.
    - On HTTP 400 or 401 from refresh, it clears the session and returns null. Local data is never touched.
  - `authFetch(path, init) -> Promise<Response>`: adds the `apikey` and `Authorization: Bearer` headers.
  - `signOut() -> Promise<void>`: best-effort `POST /auth/v1/logout`, then clears kv `session`.
  - `onAuth(fn) -> unsubscribe`
- `tests/fake-supabase.mjs`: `installFakeSupabase(page, { remote = null, failUploads = false })` routes `**/auth/v1/authorize**` (redirect back with `?code=test`), `**/auth/v1/token**`, `**/rest/v1/user_data**` (GET returns `remote`, POST stores it), `**/rest/v1/user_push**` and `**/rest/v1/rest_alarms**`. **Interfaces (produced):**
- `src/core/sync.mjs`:
  - `decideSync({ local, remote, meta }) -> { action: 'none'|'push'|'pull'|'merge' }`. `meta` is `{ dirtyAt: number|null, syncedRemoteAt: number|null }` (kv `sync`). `remote` is `null` or `{ data, updatedAt }`. Rules, in order:
    1. `remote == null` → `push` if local has a profile or any workouts, else `none`
    2. `syncedRemoteAt == null` (first sign-in on this phone) → `merge` when local has workouts, else `pull`
    3. `remote.updatedAt > syncedRemoteAt` and `dirtyAt == null` → `pull`
    4. `remote.updatedAt > syncedRemoteAt` and `dirtyAt != null` → `push` when `dirtyAt > remote.updatedAt`, else `pull` (the last change wins)
    5. `dirtyAt != null` → `push`
    6. otherwise `none`
  - `tooBig(json: string) -> boolean`: UTF-8 bytes > `MAX_SYNC_BYTES`.
- `src/ui/sync.js`:
  - `startSync() -> void`: subscribes to store and settings changes and sets `dirtyAt`, debounced `SYNC_DEBOUNCE_MS`. It runs `syncNow()` on start, on `online`, and on `visibilitychange` to visible.
  - `syncNow() -> Promise<'ok'|'offline'|'too-big'|'signed-out'>`:
    - **push:** upsert `user_data` with `{ data, app_version, updated_at: now }` and, on the first push, `consent_at` and `consent_version`. On success, set `syncedRemoteAt = updated_at` and `dirtyAt = null`. On failure, leave `meta` unchanged.
    - **pull:** `applyImport({ data: remote.data }, 'replace')`, set `syncedRemoteAt`, then `location.reload()`.
    - **merge:** `mergeData(local, remote.data)`, push it, then apply it locally.
  - `syncState`: `{ status, lastOkAt }`, used by settings.
